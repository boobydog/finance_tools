# システム概要

## 1. 目的

日本株(東京証券取引所上場銘柄)を対象に、以下4つの投資判断を**機械的・再現可能なルール**で支援するツールを提供する。個別株の裁量判断に頼りすぎず、あらかじめ定義した基準に基づいて判定結果を提示することを目的とする。

1. **候補スクリーニング**: ファンダメンタルズ・テクニカルの両面から、投資対象として妥当な銘柄を自動的に「候補」として発見する。
2. **買入タイミング判定**: 候補銘柄(および買い増し・再エントリーを検討する保有中/売却済銘柄)について、「今が買い時か」を判定する。
3. **損切り判定**: 保有銘柄について、損切りすべきかを判定する。
4. **利確判定**: 保有銘柄について、利益確定すべきかを判定する。

判定基準(スクリーニング条件・買入タイミング条件・損切り条件・利確条件)は、銘柄の時価総額規模(小型株/中型株/大型株)などのセグメントごとに異なる値を設定できる必要がある。すべての基準値は設定画面から変更可能でなければならない(ハードコードしない)。

## 2. 対象ユーザー

個人投資家が自分専用に運用する想定(マルチテナント設計は不要)。認証は簡易な単一管理者アカウント(ユーザーテーブル不要)で十分。

## 3. 対象銘柄の範囲

日本株(東証上場銘柄)を対象とし、既定の銘柄ユニバースは日経225(日経平均株価)構成銘柄とする。

- 新規銘柄の発見(候補スクリーニング・テクニカルスコアリングの対象探索)は、日経225の構成銘柄(日本経済新聞社の公式サイトから取得)を対象に行う。
- 日経225の構成銘柄は入れ替わりがあるため、定期的に最新の構成銘柄リストと同期する。
- 一度何らかのステータス(候補/保有中/売却済/除外)が設定された銘柄は、その後日経225の構成銘柄から外れても追跡対象から外さない。
- したがって実際の追跡対象銘柄は「日経225構成銘柄」∪「過去に何らかのステータスが設定された銘柄」の和集合となる。

## 4. システム構成(3層アーキテクチャ)

```
┌─────────────────┐      ┌──────────────────┐      ┌─────────────┐
│  frontend        │ ──▶  │  app (api)        │ ──▶  │  db         │
│  Next.js 16      │ HTTP │  FastAPI          │ SQL  │  MySQL 8.4  │
│  (App Router)    │      │                   │      │             │
└─────────────────┘      └──────────────────┘      └─────────────┘
                                    ▲
                                    │ 同一イメージ、コマンド違いで cron実行
                          ┌──────────────────┐
                          │  app (batch/cron) │
                          │  同じPythonコード │
                          └──────────────────┘
```

- **db**: MySQL 8.4。スキーマは番号付きマイグレーションファイル(`mysql/init/`)で管理する。
- **app**: Python(FastAPI)。REST APIサーバーと、定期実行バッチ(cron)の2役を、同一コードベース・同一Dockerイメージから起動コマンドの違いで使い分ける。
- **frontend**: Next.js(App Router) + MUI + TanStack Query。

Docker Composeで4つのコンテナ(frontend / api / app(cron) / db)を構成する。詳細は [`app/batch_and_infra.md`](../app/batch_and_infra.md) を参照。

## 6. 非機能要件

- **判定基準の可変性**: スクリーニング条件・買入タイミング条件・損切り条件・利確条件のすべての項目(閾値・配点・期間など)は、コードを変更せずに設定画面から編集できること。
- **セグメント別設定**: 銘柄の時価総額規模(小型株/中型株/大型株)ごとに異なる基準値を設定できること。基準値の集合を「スクリーニンググループ」という単位で管理し、銘柄ごとにどのグループの基準を適用するかを解決できること。
- **外部API呼び出しの制御**: yfinance等の外部APIは呼び出し回数に制約があるため、(a) ローカルDBキャッシュを優先的に使う、(b) バッチ処理はリトライ制御・実行間隔制御を持つ、(c) 一括取得はチャンク分割する、という設計を必須とする。
- **文字コード**: 日本語データを扱うため、DB接続・DDL適用時は`utf8mb4`を明示指定すること(文字化け対策)。
- **冪等性**: バッチ処理(候補スクリーニング適用・スコア再計算等)は、既にユーザーが手動でステータスを設定した銘柄を上書きしないこと。
