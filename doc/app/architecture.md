# バックエンド設計原則(app)

同一のPythonコードベース・同一のDockerイメージを、起動コマンドの違いで2つの役割に使い分ける。

| サービス | 起動コマンド | 役割 |
|---|---|---|
| `api` | `uvicorn api.main:app --reload` | REST APIサーバー(フロントエンドからのリクエストに応答) |
| `app` | `/entrypoint.sh`(既定CMD、内部で`cron -f`) | 定期実行バッチ(cron) |

## 1. SQLはPythonに埋め込まない(SQL方針)

DML/DQL(SELECT/INSERT/UPDATE/DELETE)はすべて`.sql`ファイルとして`batch/sql/`配下に独立させ、Python側はSQLAlchemy Core経由でファイルを読み込んで実行するだけにする。ORMのクエリビルダは使わない。

- `scripts/sql_runner.py`の`load_sql(filename)`が`batch/sql/*.sql`を読み込む。
- `execute_many(engine, filename, params_list)`が複数パラメータセットの一括実行(バルクupsert等)を担う。
- この方針の目的: SQLを直接読み書きできるようにし、複雑な集計・JOINをPython側のロジックに埋め込まない。

この設計方針は新規実装でも踏襲すること。1機能につき1〜数個の`.sql`ファイルを作る想定で構わない。

## 2. バックグラウンド更新パイプライン

候補スクリーニング・テクニカルスコア・各種指標は、ユーザーの画面操作(一覧表示・設定変更等)をトリガーに**非同期(FastAPIの`BackgroundTasks`)で**再計算する。同期的に全銘柄を再計算すると画面応答が遅くなるため。

- `scripts/pipeline.py`の`refresh_metrics_and_screening(engine)`が中心的なオーケストレーター。
- 二重実行防止のため`threading.Lock`で排他制御する(既に実行中なら新しいトリガーはスキップ)。
- 処理内容(順序): (1) 対象銘柄群の解決 → (2) テクニカルスコアリング → (3) テクニカル指標更新 → (4) 候補スクリーニング再評価 → (5) ターゲットプライス再計算 → (6) トレイリングストップ基準値(保有期間中の最高値)更新。
- ファンダメンタルズ(PER/PBR/ROE等)は決算時にしか変わらないため、このパイプラインには含めない。別途cronの日次バッチで更新する。

## 3. 対象銘柄群の解決方針

`scripts/target_symbols.py`の`resolve_target_symbols(engine)`が、バッチ処理・パイプラインの両方から共通で使う「今回処理すべき銘柄一覧」を返す。

```
対象銘柄 = (候補/保有中/売却済/除外 のいずれかのステータスを持つ銘柄)
         ∪ (日経225の現在の構成銘柄)
```

日経225構成銘柄の取得は日経公式サイトのCSVから行う(`scripts/nikkei225.py`)。取得のたびに`stocks.is_nikkei225`フラグを同期する。

## 4. 外部API呼び出しの制御方針

yfinance・JPX公式サイト・日経公式サイト・EDINET(金融庁)は、非公式または呼び出し回数に制約のある外部データソースである。以下のパターンを徹底する。

- **ローカルキャッシュ優先**: `daily_stock_data`をキャッシュとして使い、2回目以降は差分(前回保存日の翌日以降)のみ取得する(`technical_screener._fetch_history`)。EDINETについても`edinet_filings`台帳で取込済みのdoc_idを記録し、日次スキャンで再取得しない。
- **チャンク分割**: 一括取得は`scripts/yfinance_batch.py`の`chunked(items, batch_size=20)`で20件ずつに分割する。
- **リトライ・実行間隔制御**: `scripts/batch_logger.py`が、cron自体は高頻度(例: 5分おき)で起動しても、実処理は指定した最小間隔(例: 24時間)でしか実行しない仕組みを提供する。失敗時は5分→30分→1時間の間隔で最大3回リトライし、状態は`batch_logs`テーブルに永続化する(コンテナ再起動をまたいでも状態が保たれる)。
- **リクエスト間隔の明示的な制御**: EDINETは公式なレート制限が非公開のため、`scripts/edinet_client.py`は書類一覧取得・書類ダウンロードそれぞれに固定のsleep間隔(`LIST_REQUEST_INTERVAL_SECONDS`/`DOWNLOAD_REQUEST_INTERVAL_SECONDS`)を設けている。
- **APIキーの扱い**: EDINETのAPIキーはURLクエリパラメータとして送信する仕様のため、`requests`の例外メッセージにそのまま含まれてしまう(ログ経由の漏洩リスク)。`edinet_client.py`の`_get()`はこれを避けるため、例外発生時にURLを伏せた別の例外へ置き換えてからログに渡す。新しい外部APIキーを扱うクライアントを追加する場合もこのパターンに従うこと。

新しい外部データ取得バッチを追加する場合も、このリトライ・間隔制御パターンに従うこと。

## 5. スクリーニンググループの解決方針(判定エンジン共通)

買入タイミング・損切り・利確判定のいずれも、評価対象の銘柄がどのグループの基準を使うかを、以下の優先順で解決する(`scripts/trade_judgment_engine.py`の`resolve_group`)。

1. 銘柄が持つタグ(候補になった際の根拠グループ名)のうち、有効なグループに一致するものがあれば、そのグループの基準を使う(複数該当時は`group_id`が最小のものを優先)。**一致したグループの基準のみを使い**、そのグループにルールが無くてもデフォルトグループへはフォールバックしない。
2. タグが一致するグループが無ければ、`is_default=true`の削除不可グループにフォールバックする。
3. 有効なグループが1件も無ければ、判定対象外(未設定)として扱う。

**既に保有中・除外等のステータスが設定された銘柄は、候補スクリーニング(系統A/B)による自動タグ付けの対象外**(原則6参照)。そのため、後から作成したグループの基準を既存の保有銘柄に適用したい場合、自動では絶対にタグが付かない。この場合は`POST /api/stocks/{ticker}/tags`でグループ名と同じタグを手動付与することで、次回の判定エンジン評価からそのグループの基準を適用できる。

## 6. 冪等性・上書き禁止の原則

候補スクリーニングやスコアベースの自動候補化は、**既にステータスが設定されている銘柄(手動含む)を上書きしない**。これにより、ユーザーが意図的に「除外」や「候補」に設定した銘柄が、バッチ処理によって勝手に変更されることを防ぐ。

グループを無効化した場合や、しきい値を変更した場合は、そのグループ/しきい値のみを根拠に候補化されていた銘柄をリセットし、再評価する「reconcile」処理を用意すること(`reconcile_inactive_group_candidates`、`reconcile_stale_score_candidates`)。

## 7. 複数回の売買(複数ロット)への対応方針

同一銘柄を複数回に分けて買い増し・売却することを前提とする。

- 保有数・平均取得単価は`user_stock_status`に保存せず、`trade_history`全体を都度**加重平均で集計**する(直近1回の取引だけを見ない)。
- 口座種別(特定/一般 vs NISA)は税制上別勘定のため、**口座種別ごとに残存数量・加重平均取得単価を分けて計算**し、手数料・税金計算もそれぞれ独立に行ってから合算する。
- 部分売却では、残存数量が0を超えていれば`holding`ステータスを維持する。全数量を売り切った時点で初めて`sold`にする。
- 新規の買い(ポジションを新たに開く場合)でのみ、購入時スコア・トレイリングストップ基準値・購入時ターゲットプライスをスナップショットする。既存ポジションへの買い増しでは、これらの基準値を上書きしない(最初にポジションを開いた時点の基準を保持する)。

## 8. レガシー機能の扱い

以下は初期実装または過去の移行作業の名残であり、現行の主要フローには含まれない。新規実装では踏襲するかどうかを判断してよい。

- `scripts/stock_screener.py` / `scripts/stock_fetcher.py`: yfinance組み込みスクリーナーAPI(`yf.screen`)を使った、DB非依存のCLI専用スクリーニング機能。
- `scripts/legacy_screen_config.py`: 旧JSON形式(`config/screen_conditions*.json`)の条件を、現行のDB駆動`screening_groups`/`screening_rules`モデルへ変換する一度限りの移行ツール。
